# 微信对话人工验收手册

## 验收目的

本手册用于维护者在真实微信聊天窗口中，逐项验收微信渠道的登录、访问控制、消息收发、媒体接收、引用、附件回传和会话连续性。

本手册只记录用户能够通过微信界面、Harness 控制面和脱敏日志观察到的结果。Agent 回复受所选模型影响，不要求逐字一致；只要求回复包含各用例指定的可核验信息，且不编造未取得的内容。

当前微信渠道只支持私聊。语音和视频的验收边界如下：

- 语音内容能否被复述，依赖微信上游是否提供语音转写文本；这不是 Harness 原生音频理解能力。
- 视频仅验收下载、解密、附件保存和类型识别；不要求模型理解视频画面或声音。

## 验收前准备

### 一、账号与环境

1. 准备一个用于扫码登录的微信测试账号，记为“所有者账号”。
2. 准备另一个微信账号，记为“未授权账号”，用于验证拒绝访问；不要使用不知情人员的账号。
3. 使用当前待验收代码构建并启动 Harness，保持渠道调试日志可见：

```powershell
pnpm build
pnpm channels weixin
pnpm web:debug
```

4. 在 Harness 渠道设置中启用微信，并确认“安全访问”使用“仅当前扫码微信账号”。
5. 测试期间不要切换模型、工作区或访问策略，以免结果无法互相比较。

### 二、测试材料

所有材料均使用非敏感内容。

1. 图片：制作一张清晰的图片，画面中只写 `微信图片验收-2468`，保存为 `微信图片验收.png` 或 `微信图片验收.jpg`，建议小于 2 MiB。
2. 文本文件：创建 `微信文件验收.txt`，文件内容只写一行 `微信文件内容-2468`，建议小于 1 MiB。
3. 视频：准备一段 3 至 5 秒的 MP4 文件，文件名为 `微信视频验收.mp4`，建议小于 10 MiB。
4. 语音内容：准备在安静环境中清楚朗读“微信语音验收二四六八”。
5. 较慢问题：准备复制以下文字，用于观察“正在输入”状态：

```text
请分三点比较水循环中蒸发、凝结和降水的作用，每点写两句话，最后给一句总结。
```

### 三、证据记录规则

每个用例记录：用例编号、执行时间、执行账号、通过或失败、微信界面截图，以及对应的脱敏后台日志。

允许记录稳定的消息标识、会话标识、附件名称、媒体类型、字节数、访问控制结果和连接状态。禁止记录或粘贴以下内容：

- 二维码正文或二维码解析结果
- 登录令牌、授权请求头或凭据文件
- AES 密钥
- 带签名的媒体地址
- 完整平台原始载荷
- 文件正文或媒体二进制内容

## 对话验收用例

### 微信-001：首次扫码登录与所有者识别

**前置条件**

- 本地没有该微信渠道账号的有效登录凭据。
- “所有者账号”尚未在本次环境中扫码。

**在微信输入或发送什么**

1. 在 Harness 微信渠道设置中开始扫码授权。
2. 使用“所有者账号”扫描二维码并在手机上确认。
3. 渠道显示已连接后，在微信中发送：

```text
微信所有者验收-2468，请回复这个编号。
```

**Harness 应返回什么**

- 扫码过程中无需产生聊天回复。
- 登录成功后，应在同一微信私聊中回复，并包含 `微信所有者验收-2468`；措辞可以不同。

**微信界面观察**

- 扫码确认后不应反复要求重新扫码。
- 测试消息只收到一次回复。
- Harness 的“安全访问”应将扫码账号识别为当前所有者，并保持仅所有者可用。

**日志或后台证据**

- 授权状态进入已认证，连接状态进入已连接。
- 所有者身份来自扫码账号的规范化用户标识，不是根据昵称猜测。
- 浏览器响应和日志中没有二维码正文、令牌或凭据内容。

**通过标准**

- 登录、所有者识别和首次文本往返全部成功，且没有秘密信息泄漏。

### 微信-002：普通文本往返与单次处理

**前置条件**

- 微信渠道已连接。
- 使用“所有者账号”。

**在微信输入或发送什么**

```text
微信文本验收-2468。请只说明你收到的验收编号。
```

**Harness 应返回什么**

- 回复应包含 `微信文本验收-2468`。
- 不要求回复逐字固定，但不得替换或遗漏编号。

**微信界面观察**

- 回复出现在发送消息的同一私聊中。
- 等待至少 40 秒，不能出现第二条由同一输入触发的重复回复。

**日志或后台证据**

- 只有一条对应的入站摘要和一次 Agent 处理记录。
- `channel-weixin` 入站摘要包含稳定的消息标识、会话标识和文本部分摘要，不包含消息全文或平台原始载荷。

**通过标准**

- 编号正确、会话正确、只处理一次且只回复一次。

### 微信-003：图片文字识别

**前置条件**

- 已准备 `微信图片验收.png` 或 `微信图片验收.jpg`。
- 当前所选模型支持图片理解。

**在微信输入或发送什么**

1. 发送准备好的图片。
2. 紧接着发送：

```text
请读取我刚才图片中的文字，只回复验收文字。
```

**Harness 应返回什么**

- 回复应包含 `微信图片验收-2468`。
- 允许有少量说明文字，但不能把附件占位符当作识别结果。

**微信界面观察**

- 图片在微信中发送成功。
- 回复能够对应刚发送的图片，不要求用户再次上传。

**日志或后台证据**

- 图片摘要包含 `resourceRef`、正确的图片媒体类型和大于零的 `localDataBytes`。
- 成功路径不存在 `ingressFailure`。
- 日志不包含带签名的媒体地址、AES 密钥或图片二进制内容。

**通过标准**

- 模型正确读出验收文字，并且日志证明图片已经完成本地取回，而不是只收到图片占位符。

### 微信-004：文本文件读取

**前置条件**

- 已准备 `微信文件验收.txt`。
- 通用文件扩展已启用。

**在微信输入或发送什么**

1. 发送 `微信文件验收.txt`。
2. 随后发送：

```text
请读取我刚才发送的文本文件，只回复文件中的验收内容。
```

**Harness 应返回什么**

- 回复应包含 `微信文件内容-2468`。
- 不要求逐字固定，但不能只回复“收到文件”或文件名。

**微信界面观察**

- 文件发送成功，随后收到一条与文件内容对应的回复。

**日志或后台证据**

- 文件摘要包含名称 `微信文件验收.txt`、合理的文本媒体类型、非零大小和大于零的 `localDataBytes`。
- 成功路径不存在 `ingressFailure`。
- 模型侧使用私有附件描述和文件读取能力，不接触带签名的媒体地址。

**通过标准**

- 回复中的验收内容正确，且后台证明确实保存并读取了该附件。

### 微信-005：微信语音接收与平台转写

**前置条件**

- 在安静环境中使用“所有者账号”录制语音。

**在微信输入或发送什么**

1. 发送一条微信语音，清楚朗读：

```text
微信语音验收二四六八
```

2. 随后发送：

```text
如果上一条语音带有平台转写，请复述转写内容；如果没有，请明确回复“未取得平台转写”。
```

**Harness 应返回什么**

- 如果微信上游提供转写，回复应包含“微信语音验收二四六八”或等价数字写法。
- 如果微信上游未提供转写，回复应明确说明未取得平台转写，不能猜测语音内容。

**微信界面观察**

- 语音发送成功，后续文本请求得到回复。
- 即使没有平台转写，渠道也不应断开，后续文本消息仍能正常往返。

**日志或后台证据**

- 音频摘要显示大于零的 `localDataBytes`。
- SILK 解码成功时媒体类型应为 WAV；无法解码时可保留为 SILK，但不能丢弃整条消息或中断接收循环。
- 日志不包含音频正文、媒体地址或 AES 密钥。

**通过标准**

- 音频成功取回；有平台转写时能正确复述，无平台转写时诚实说明且渠道继续可用。
- 本用例不得据此宣称 Harness 具备原生音频理解能力。

### 微信-006：视频接收与附件保存

**前置条件**

- 已准备 `微信视频验收.mp4`。
- 通用文件扩展已启用。

**在微信输入或发送什么**

1. 发送 `微信视频验收.mp4`。
2. 随后发送：

```text
请确认我刚才发送的附件类型；如果能取得文件名和大小，也一并告诉我。不要描述视频画面。
```

**Harness 应返回什么**

- 回复应确认收到的是视频附件。
- 只有在附件描述中确实取得文件名或大小时才能给出这些信息；不能猜测视频内容。

**微信界面观察**

- 视频在微信中发送成功。
- 回复只确认附件事实，不以虚构的画面分析作为通过依据。

**日志或后台证据**

- 视频摘要显示 `video/mp4` 或与实际文件一致的媒体类型，并有大于零的 `localDataBytes`。
- 成功路径不存在 `ingressFailure`。
- 附件已进入私有存储，日志不包含带签名的媒体地址或视频二进制内容。

**通过标准**

- 视频已完成接收和保存，Agent 能确认附件类型，且没有声称未经验证的视频内容理解能力。

### 微信-007：引用文本上下文

**前置条件**

- 微信渠道已连接。

**在微信输入或发送什么**

1. 先发送：

```text
被引用的内容是：微信引用文本-2468
```

2. 在微信中长按该消息，选择引用。
3. 在引用状态下发送：

```text
请告诉我引用消息中的验收编号。
```

**Harness 应返回什么**

- 回复应包含 `微信引用文本-2468`。
- 当前问题和被引用内容都应只出现一次，不应把引用误认为一条新的独立用户消息。

**微信界面观察**

- 发送时能看到微信原生引用样式。
- 回复与所引用的那条文本相符。

**日志或后台证据**

- 入站结构中保留了受限的引用上下文。
- 日志和模型输入不暴露完整平台原始引用载荷。

**通过标准**

- 引用内容准确、无重复、无平台原始载荷泄漏。

### 微信-008：引用媒体的安全上下文

**前置条件**

- 已完成图片或视频发送。

**在微信输入或发送什么**

1. 在微信中引用此前发送的图片或视频消息。
2. 在引用状态下发送：

```text
请只告诉我引用的是图片还是视频；不要猜测媒体内容。
```

**Harness 应返回什么**

- 回复应正确说明引用的是图片或视频。
- 不要求重新识别被引用媒体的内容，也不得编造画面信息。

**微信界面观察**

- 当前消息显示正确的微信原生引用关系。
- 回复中的媒体类型与被引用消息一致。

**日志或后台证据**

- 引用上下文只包含受限的媒体类型摘要。
- 日志和模型输入不包含带签名的媒体地址、AES 密钥或完整原始引用载荷。

**通过标准**

- 媒体类型正确，引用上下文受到限制且没有敏感信息泄漏。

### 微信-009：文件附件原样回传

**前置条件**

- 已通过“微信-004”成功保存 `微信文件验收.txt`。
- 通用文件扩展和渠道消息发送工具已启用。

**在微信输入或发送什么**

```text
请把我刚才发送的“微信文件验收.txt”作为文件附件原样发回给我，并在消息中写“微信文件回传-2468”。
```

**Harness 应返回什么**

- 应返回名为 `微信文件验收.txt` 的文件附件。
- 文本回复或附件附言应包含 `微信文件回传-2468`；具体分成几条消息不作固定要求。

**微信界面观察**

- 收到的是可下载的文件附件，而不是文件内容截图或仅有文件路径的文本。
- 下载并打开文件后，内容仍为 `微信文件内容-2468`。
- 同一附件不应被重复发送。

**日志或后台证据**

- 渠道发送工具记录投递成功。
- 日志可记录附件名称、类型和大小，但不能记录文件正文、媒体地址、令牌或 AES 密钥。

**通过标准**

- 文件名和内容保持不变、文件可下载、附言可识别且只投递一次。

### 微信-010：“正在输入”状态与失败降级

**前置条件**

- 当前微信账号或客户端可能支持“正在输入”提示。

**在微信输入或发送什么**

发送准备好的较慢问题：

```text
请分三点比较水循环中蒸发、凝结和降水的作用，每点写两句话，最后给一句总结。
```

**Harness 应返回什么**

- 最终应返回符合问题要求的三点比较和一句总结。
- 是否出现“正在输入”不能影响最终回复内容。

**微信界面观察**

- 在当前账号和客户端支持时，最终回复前可见“正在输入”提示。
- 如果平台不支持或提示未出现，最终回复仍应正常到达。

**日志或后台证据**

- 获取或发送输入状态失败时只能作为非致命问题记录，不能中断消息处理。
- 连续执行本用例两次时，不应出现明显的配置请求风暴。

**通过标准**

- 最终回复始终成功；支持该能力的账号出现输入提示，不支持时能够无损降级。

### 微信-011：正常重启后免扫码与消息去重

**前置条件**

- 已完成首次扫码登录并成功收发消息。

**在微信输入或发送什么**

1. 重启前发送：

```text
微信重启前-2468，请回复这个编号。
```

2. 等待回复后正常停止并重新启动 Harness，不删除任何凭据或存储。
3. 重启后不要扫码，直接发送：

```text
微信重启后-2468，请回复这个编号。
```

**Harness 应返回什么**

- 重启前的回复包含 `微信重启前-2468`。
- 重启后的回复包含 `微信重启后-2468`。
- 重启后不得再次回复第一条消息。

**微信界面观察**

- 重启后无需重新扫码。
- 两条测试消息各有且只有一条对应回复，均位于同一私聊。

**日志或后台证据**

- 重启后从安全存储恢复凭据并重新进入已连接状态。
- 已处理消息游标或去重状态生效，没有重放重启前消息。
- 日志不打印恢复出的令牌。

**通过标准**

- 免扫码恢复成功，重启前后消息各处理一次，无漏回和重复回复。

### 微信-012：已绑定重定向恢复

**前置条件**

- 已完成首次扫码登录，本地仍保存有效凭据。
- 微信渠道当前可正常收发文本。

**在微信输入或发送什么**

1. 在 Harness 微信渠道设置中再次开始扫码授权流程。
2. 如果平台提示账号已绑定或直接恢复授权，按页面提示完成操作。
3. 状态稳定后，在微信发送：

```text
微信已绑定恢复-2468，请回复这个编号。
```

**Harness 应返回什么**

- 授权状态切换过程中无需产生聊天回复。
- 恢复后应回复并包含 `微信已绑定恢复-2468`。

**微信界面观察**

- 平台返回 `binded_redirect` 时，渠道应恢复到已认证和已连接，而不是停留在等待扫码或循环报错。
- 恢复后测试消息只收到一次回复。

**日志或后台证据**

- 授权流程内部使用本地令牌列表，但日志和浏览器响应不显示令牌值。
- 可观察到已绑定重定向后的认证与监听恢复；不能出现持续重连风暴。

**通过标准**

- 已绑定重定向路径完成恢复，消息收发恢复正常，且秘密信息未泄漏。
- 如果本次平台没有返回 `binded_redirect`，记录为“未触发”，不能据此判定该分支通过。

### 微信-013：未授权账号安全拒绝

**前置条件**

- “所有者账号”已经扫码登录。
- 安全访问保持“仅当前扫码微信账号”。
- “未授权账号”能够向该微信入口发起私聊。

**在微信输入或发送什么**

1. 使用“未授权账号”发送：

```text
微信未授权测试-2468，请回复这个编号。
```

2. 再发送：

```text
/stop
```

3. 切回“所有者账号”发送：

```text
微信所有者仍可用-2468，请回复这个编号。
```

**Harness 应返回什么**

- 对“未授权账号”的两条消息保持静默，不发送拒绝提示，也不进入 Agent。
- 对“所有者账号”的消息正常回复，并包含 `微信所有者仍可用-2468`。

**微信界面观察**

- “未授权账号”收不到任何 Harness 回复。
- “所有者账号”仍能正常对话，未授权 `/stop` 没有中断其使用。

**日志或后台证据**

- `channel-access` 记录未授权私聊被拒绝，原因应为用户不在允许列表或等价的安全拒绝原因。
- 未授权消息发生在命令解析、会话绑定、Agent 创建和其他本地副作用之前。
- 访问日志不记录消息正文、发送者昵称、令牌、媒体或平台原始载荷。

**通过标准**

- 未授权账号完全无法驱动 Agent、命令或会话副作用；所有者账号不受影响。

## 建议执行顺序

1. 先执行“微信-001”至“微信-004”，确认登录、文本、图片和文件主链路。
2. 再执行“微信-005”至“微信-010”，确认语音、视频、引用、回传和输入状态。
3. 然后执行“微信-011”和“微信-012”，确认凭据与状态恢复。
4. 最后执行“微信-013”，验证访问控制保持默认拒绝。

## 本手册不覆盖的验证

以下项目无法仅凭微信聊天窗口可靠证明，因此不属于本手册的通过条件：

- 媒体发送载荷中的长度、加密类型、媒体类型和其他协议字段是否逐字段正确
- AES 密钥在发送载荷中的具体编码形式
- 上传地址、分块上传和媒体下载请求的内部协议细节
- 腾讯上游版本、提交号和契约夹具是否完全一致
- 自动化契约测试、单元测试、清单校验和发布门禁是否通过

这些项目必须通过源码核验、结构化契约测试、脱敏协议夹具或独立的受控平台验证完成，不能用“微信界面看起来正常”替代。

## 总体通过条件

- 所有实际触发的高优先级对话链路均通过；未触发的 `binded_redirect` 单独标记，不得误报通过。
- 成功接收的图片、文件、音频和视频均有大于零的 `localDataBytes`，且成功路径没有 `ingressFailure`。
- 每条用户消息至多触发一次 Agent 处理和一次预期投递，不出现重复回复或重启重放。
- 未授权账号始终在产生本地副作用前被静默拒绝，所有者账号正常可用。
- 日志、截图和后台证据均不包含二维码正文、令牌、AES 密钥、带签名的媒体地址、完整原始载荷或文件正文。
- 任何失败都记录用例编号、时间、脱敏后的实际结果和预期结果，不以猜测补全证据。
